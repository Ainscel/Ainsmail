# 账号模块架构审阅（可维护性 / 可扩展性）

更新日期：2026-11-16  
范围：Task 1 账号接入相关代码（`security/`、`ui/account/`、`ui/settings` 账号与密钥、`MailApp` 登录编排、`MailboxViewModel` 样例切换、壳层头像列）

## 总评

不是屎山，也不是在回环授权遗留上继续堆。Gmail 已改为 Android 客户端 + Play 授权，运行时旧路径已清；核心做到「界面只见 `Account`，凭证留在加密文件」。

真正要警惕的是三处会随 Task 2（收信）迅速恶化的雏形：

1. `security/` 包职责过载（加密、账号 CRUD、头像、Google HTTP 同包）
2. 登录编排状态散落在根壳 `MailApp`
3. 尚无面向同步层的凭证出口与令牌生命周期闭环

## 做得好的部分（应保留）

- 凭证与展示分离：`AccountBook` 只发布 `model.Account`；token / 授权码不进 Compose / 会话
- 分写不互毁：`replacingSecrets` / `replacingAccounts` 保证改 DeepSeek 不清账号
- 登录与邮箱 VM 解耦：订阅 `book.directory`，用 `UseRealAccounts` / `ReplaceAccounts` / `RestoreSamples` 切样例
- 领域规则外置：`AccountRules` 管地址与 Gmail 门槛
- 回环遗留已清：无 `127.0.0.1` / offline refresh 运行时代码

## 问题与处置

### P0 — 收信前必须先定边界

| 问题 | 处置 |
|------|------|
| 缺少同步层凭证出口 | `AccountBook.credentialsFor(id)` + `ProviderCredentials` sealed；禁止进入 UI state |
| Gmail accessToken 只写不养 | 过期判定落 data（`gmailAccessExpired`）；需用户再授权时由上层消费 sealed 结果 |

### P1 — 高耦合 / 低内聚雏形

| 问题 | 处置 |
|------|------|
| 设置层反向依赖 `ui.account` | `AccountError` 与 `AccountWrite` 同层；`readImage` 迁出 UI 包 |
| 登录对话框布尔堆在 `MailApp` | 提供商 / QQ 步骤收进 `AccountLoginViewModel` |
| 双 `SecretStore` 实例 | 装配时共享同一实例 |
| `security/` 包物理迁入 `data/` | 可与后续收信同批；本次先定边界，不强制整包搬家 |

### P2 — Rule of Two / 体积红线

| 问题 | 处置 |
|------|------|
| QQ 与设置各写一套图片选择 | `rememberAccountImagePicker` |
| `ApiException` 映射两套 | 合并到 Google 登录一侧 |
| `AvatarColumn` / `AvatarScroller` 过长 | 拆出 scroller；头像解码与业务布局分离 |

### P3 — 韧性与语义（记录，不阻塞本轮）

- Schema 2→3 静默丢弃 refreshToken，升级用户可能出现空令牌 Gmail 记录 → 后续 `needsReauth` / 引导重登
- 解密失败直接删文件 → 宜先备份再标 `Unreadable`
- Gmail 空 token 映射成 `BlankCode` 再拧成 `Rejected` → 语义收紧
- `AccountBook` / `SecretStore` 缺单测 → 收信改写前补内存假 store

## 明确不是的问题

- 样例 + 真账号不是双源持久化：磁盘只有 Book；会话是去规范化副本 + demo 闸门
- 不需要立刻上 Repository / UseCase
- `AccountLoginViewModel` 体量临界可接受；真正该收的是根壳对话框状态

## 明确不做

- 空 Repository、按 Provider 的 UseCase 类
- 把凭证放进 `MailboxSession`
